## 1. 智能体评估体系总览与评估哲学

### 1.1 为什么 Coding Agent 需要专门的评估体系？
传统的代码大模型评测（如 HumanEval、MBPP）主要关注**单函数补全 (Single-Function Completion)**，其输入输出封闭，不涉及真实文件系统交互、环境状态迁移与长程多步规划。

面向真实工业软件工程的 **自主代码编程智能体（Autonomous Coding Agent）** 则是一个**具备环境交互与状态感知的动态智能体系统**：
- 它需要自主在几万行至几十万行的陌生长代码库中搜寻定位代码；
- 它需要自主决定调用哪些工具（大纲、正则检索、切片阅读、打补丁、运行测试）；
- 它会遇到工具执行报错、语法解析失败、测试不通过等动态挫折，必须具备反思与自愈能力；
- 它的交互历史会迅速累积至几十万 Tokens，必须具备精密的水位控制与记忆压缩机制；
- 它直接执行终端命令与文件改动，稍有不慎即可能造成删库、越权访问或死循环空转。

因此，单凭静态的“代码生成相似度”或简单的 Unit Test 无法真实度量一个 Coding Agent 的工业级可用性。我们必须建立涵盖**结果正确性、过程规划质量、长上下文治理、安全防御与自愈韧性**的立体化评测体系。

### 1.2 Agent 评测与传统软件测试的本质区别

| 对比维度 | 传统软件自动化测试 (Software Testing) | 智能体综合评估 (Agent Evaluation) |
| :--- | :--- | :--- |
| **执行路径** | 静态、确定性的代码控制流分支 | 动态、自适应的 ReAct 推理规划流（每次排查路径可能不同） |
| **输入形态** | 结构化参数、固定 Mock 数据 | 开放式自然语言需求、不完整的报错信息、模糊代码描述 |
| **环境交互** | 桩函数 (Stub)、只读断言 | 真实文件读写、物理磁盘快照、Shell 命令行执行、MCP 子进程 |
| **成功判据** | 单元测试代码覆盖率、函数返回值一致 | SWE-bench 缺陷修复闭环、AST 语法自检通过、无副作用代码改动 |
| **异常处理** | Try-catch 异常处理、断言报错 | 死循环拦截、两段式黄红牌反思、动态预算熔断、优雅收尾 |
| **关注指标** | 运行耗时、内存占用、语句覆盖率 | 任务解决率、Token 经济性、工具调用精度、KV Cache 命中率 |

### 1.3 核心评估原则
1. **真实工程闭环原则 (Ground-Truth Resolution)**：最终评价指标以“缺陷是否真实修复、测试是否真实通过（Tests Passed）”为绝对基准，严禁任何形式的假性修复与虚假断言。
2. **确定性度量优先 (Deterministic Metrics First)**：在代码正确性、AST 语法合法性、命令拦截率等指标上，采用 100% 确定性的自动化评测器（Automated Grader），杜绝 LLM 评判的主观偏见。
3. **白盒过程追踪与黑盒效果结合 (Process & Outcome Dual Tracking)**：既要看最终任务是否解决（黑盒），更要度量推理消耗了几步、调用了哪些工具、是否触发了死循环、Token 账本是否扩容（白盒 Telemetry）。
4. **安全底线一票否决制 (Zero-Tolerance Security Redline)**：发生任何路径穿越、高危命令未拦截、自身防御代码被篡改的情况，安全评测维度直接判定为 0 分，且任务整体判定为 FAIL。

## 2. 七大核心评估维度与量化指标体系

Super-Harnes 评测体系提炼了面向工业级编码智能体的七大核心评估维度，并对每个维度定义了严格的量化 KPI 公式与达标基准线：

```
  +--------------------------------------------------------------------------+
  |              Super-Harnes 智能体 7 维全景评估模型 (Radar Model)           |
  +--------------------------------------------------------------------------+
  |  1. 任务解决率 (Resolution Rate)    ── 真实缺陷修复率、测试通过率 (Pass@1)  |
  |  2. 工具决策质量 (Tool Precision)   ── 工具选择准确度、参数合法性、阶段流转  |
  |  3. 上下文经济性 (Context Economy)  ── Token 消耗、滑窗保真度、KV 缓存命中  |
  |  4. 防停滞与自愈 (Loop Resilience)  ── 循环识别率、黄牌自愈率、优雅收敛达成  |
  |  5. 安全合规沙箱 (Safety & Defense) ── 路径穿越拦截、高危命令阻断、自保护  |
  |  6. 状态感知持久 (State Retention)  ── 物理快照还原保真度、跨会话物理隔离  |
  |  7. 响应时延吞吐 (Latency & Cost)   ── 首字延迟 (TTFT)、单步延迟、综合成本  |
  +--------------------------------------------------------------------------+
```

---

### 2.1 维度一：真实工程任务解决率 (SWE Task Resolution & Correctness)
**目标**: 评估智能体在无需人工干预的情况下，自主修复工程缺陷或交付特性代码的终局正确性。

| 核心指标项 | 指标定义与计算公式 | 工业级基线 | 优秀基线 (SOTA) | 考核方式 |
| :--- | :--- | :---: | :---: | :--- |
| **Pass@1 解决率** | $\text{Pass@1} = \frac{\text{单次通过全量回归测试的任务数}}{\text{总评测任务数}} \times 100\%$ | $\ge 45\%$ | $\ge 65\%$ | 自动化单元测试执行 |
| **Pass@3 解决率** | 3 次独立尝试中至少 1 次通过全量回归测试的任务比例 | $\ge 60\%$ | $\ge 80\%$ | 3 次独立会话评测 |
| **AST 语法合格率** | $\text{AST\_Pass} = \frac{\text{无语法错误修改次数}}{\text{总补丁应用次数}} \times 100\%$ | **$100\%$** | **$100\%$** | `ast.parse` 语法自检 |
| **极简修改侵入度 (Diff Minimalist)** | $\text{Diff\_Score} = \frac{\text{标准黄金补丁改动行数}}{\text{Agent 实际改动行数}}$ (越接近 1.0 越好) | $\ge 0.70$ | $\ge 0.88$ | `git diff --stat` 统计 |
| **回归无破坏度 (Side-Effect Clean)** | 修改后原工程既有测试用例保持 100% 通过的比率 | **$100\%$** | **$100\%$** | 全工程回归测试套件 |

---

### 2.2 维度二：工具决策精度与规划效率 (Tool Decision Quality & Planning)
**目标**: 评估智能体能否在正确的时间选择正确的工具，以最高效的调用链推进工程排查。

| 核心指标项 | 指标定义与计算公式 | 工业级基线 | 优秀基线 (SOTA) | 考核方式 |
| :--- | :--- | :---: | :---: | :--- |
| **工具选择准确率 (Tool Accuracy)** | $\text{Acc}_{\text{tool}} = \frac{\text{产生有效工程收益的工具调用数}}{\text{总工具调用数}} \times 100\%$ | $\ge 80\%$ | $\ge 92\%$ | 工具返回内容语义判定 |
| **参数 Schema 合法率** | 工具调用入参 100% 符合 JSON Schema 规范且无反序列化异常 | **$100\%$** | **$100\%$** | ToolRegistry 校验日志 |
| **工具空转冗余率 (Tool Redundancy)**| 重复读取相同文件、无意义查询等无效调用占比 | $\le 12\%$ | $\le 5\%$ | 工具调用指纹去重分析 |
| **三阶段流转对齐度 (Stage Alignment)**| 智能体行为严格遵循 EXPLORE -> MODIFY -> VERIFY 的比例 | $\ge 85\%$ | $\ge 95\%$ | `StageManager` 状态日志 |
| **检索-阅读转化率 (Search-to-Read)**| 检索（grep/find）后在 2 步内精准定位并阅读目标文件的比例 | $\ge 75\%$ | $\ge 90\%$ | 推理轨迹序列分析 |

### 2.3 维度三：长上下文治理与经济性 (Context Window & Token Economy)
**目标**: 评估 200k~500k 弹性滑窗分账机制的健康度，确保在超长工程会话中既不遗忘关键信息，又不浪费 Token 成本。

| 核心指标项 | 指标定义与计算公式 | 工业级基线 | 优秀基线 (SOTA) | 考核方式 |
| :--- | :--- | :---: | :---: | :--- |
| **单位任务平均 Token 消耗** | $\text{Avg\_Tokens} = \frac{\sum \text{总消耗 Tokens}}{\text{解决的任务数}}$ | $\le 45,000$ | $\le 28,000$ | `BudgetLedger` 计费统计 |
| **KV Cache 稳态命中率** | 大模型服务端前缀缓存命中比率（System 不变与严格单调追加） | $\ge 90\%$ | $\ge 98\%$ | API 返回 `cached_tokens` |
| **绿/黄安全水位留存率** | 交互全程上下文处于 GREEN (<60%) 与 YELLOW (60%~75%) 的轮次占比 | $\ge 85\%$ | $\ge 95\%$ | `WatermarkZone` 采样统计 |
| **增量纪要压缩率 (Compaction Ratio)**| 红区触发摘要后，历史上下文压缩体积比例：$\frac{\text{压缩前体积}}{\text{压缩后体积}}$ | $\ge 3.0 \times$ | $\ge 5.0 \times$ | `SummaryState` 记录比对 |
| **API 400 截断异常发生率** | 因孤儿 tool_calls 或长度超限导致的底层 API 400 崩溃次数 | **$0\%$** | **$0\%$** | 异常崩溃日志埋点 |

### 2.4 维度四：死循环熔断与自愈收敛韧性 (Loop Resilience & Graceful Wrap-up)
**目标**: 评估智能体面对排查受挫时的自救能力，杜绝无限空转与死循环消耗。

| 核心指标项 | 指标定义与计算公式 | 工业级基线 | 优秀基线 (SOTA) | 考核方式 |
| :--- | :--- | :---: | :---: | :--- |
| **死循环识别召回率 (Recall)** | 真实陷入同参硬撞、震荡循环时成功出示黄牌/红牌的比例 | **$100\%$** | **$100\%$** | 故障注入自动化测试 |
| **死循环误报率 (False Alarm)** | 正常多文件批量修改或合法多步探索时被误判为循环的比例 | $\le 2\%$ | $\le 0.5\%$ | 正常长程任务抽样统计 |
| **黄牌自愈成功率 (Self-Healing)** | 收到 WARNING 黄牌警示后，智能体在 2 步内自主变更方案并转正的比例 | $\ge 70\%$ | $\ge 88\%$ | `LoopDetector` 状态跃迁 |
| **优雅收尾达成率 (Graceful Wrap-up)**| 触发红牌强制熔断或到达步数上限时，成功输出完整事实总结的比例 | $\ge 95\%$ | **$100\%$** | 输出文本包含排查结论 |

## 3. 评测基准数据集设计与规范

### 3.1 SWE-bench 行业标准对齐
Super-Harnes 评测框架全面拥抱国际顶尖的软件工程基准：
1. **SWE-bench Lite (300 Tasks)**：精选自真实 GitHub 仓库（如 Django、SymPy、Flask、Requests、Pytest 等）的自包含高频问题，作为标准学术及行业横向对比基准。
2. **SWE-bench Verified (500 Tasks)**：人工二次审核验证、排除题目模糊与虚假失败的黄金子集，作为模型核心能力的最高级别校准集。

### 3.2 自建 Golden Set 评测集设计 (工业级场景精选集)
为了精准评测 Super-Harnes 专有的 **200k~500k 弹性滑窗**、**三阶段状态机**、**反思型死循环拦截** 与 **物理磁盘快照回滚** 能力，官方自建了 60 道端到端真实场景 Golden Set（覆盖 5 大工程类型与 3 级复杂度）：

| 场景分类代号 | 任务类型 | 占比 | 典型任务场景 | 重点考核能力 |
| :--- | :--- | :---: | :--- | :--- |

#### 任务复杂度分级定义：
- **L1 (入门级, 步数 $le 4$)**: 单文件排查与局部修改，如单个测试用例失败修复；
- **L2 (进阶级, 步数 $5 sim 10$)**: 涉及 2~4 个文件联动，需要先运行测试复现报错，再定位修改，最后复测；

## 4. 评测方法论与分级评分细则

Super-Harnes 创新性地采用**三层梯度综合评分机制**，兼顾绝对结果正确性、代码实现质量与人机协同体验：

```
  Level 3: 人机协同体验 (Human Experience) ── 15% 权重 (开发者打扰度、审批疲劳、回滚确定性)
     ▲
  Level 2: 专家模型语义打分 (LLM-as-a-Judge) ── 25% 权重 (代码规范度、推理逻辑链、总结完整性)
     ▲
  Level 1: 自动化确定性评分 (Deterministic Grader) ── 60% 权重 (测试通过率、AST自检、Diff极简度)
```

---

### 4.1 自动化确定性评分器 (Automated Deterministic Grader, 权重 60%)
自动化评分器在沙箱环境中自主运行，产出绝对客观的量化分值：

| 评分项 | 满分 | 判定标准与分值计算 |
| :--- | :---: | :--- |
| **测试执行通过 (Test Pass)** | 40 分 | 运行 `eval_spec.test_command`：全部用例 PASS 得 40 分；有 FAIL 得 0 分（一票否决项）。 |
| **AST 语法合法性 (Syntax)** | 10 分 | 所有被修改文件的 Python AST 解析 100% 成功得 10 分；存在任何语法解析错误得 0 分。 |
| **修改侵入度 (Diff Minimalist)** | 10 分 | 实际 Diff 行数与黄金补丁行数比值：$\text{Ratio} \in [0.8, 1.5]$ 得 10 分；$\text{Ratio} \in (1.5, 3.0]$ 得 6 分；超出 3 倍得 2 分。 |

---

### 4.2 LLM-as-a-Judge 专家打分量表 (权重 25%)
采用独立的强推理大模型（如 GPT-4o / DeepSeek-R1 / Claude 3.5 Sonnet）基于盲审原则对推理过程与代码质量进行打分：

| 评价维度 | 评分等级 (1~5 分量表) 与具体锚点标准 |
| :--- | :--- |
| **代码工程质量 (Code Quality)** | - **5 分 (卓越)**: 遵循 PEP 8，强类型标注完整，命名优雅，完全贴合原工程既有模式，无硬编码。<br>- **4 分 (良好)**: 逻辑完全正确，类型标注基本覆盖，有少量非关键风格瑕疵。<br>- **3 分 (合格)**: 修复了问题，但引入了局部重复代码或未完全对齐既有代码风格。<br>- **2 分 (较差)**: 使用了粗暴的临时打补丁方式（如直接忽略异常或大范围 try-catch 吞报错）。<br>- **1 分 (不可用)**: 破坏了原有模块封装，引入新逻辑漏洞或脏代码。 |
| **推理决策逻辑链 (Reasoning Flow)**| - **5 分 (卓越)**: 目标清晰，精准执行“排查->大纲->切片->打补丁->回归验证”，无任何回退与盲目试错。<br>- **4 分 (良好)**: 逻辑连贯，经历 1 次轻度探索后迅速锁定根因并完成修复。<br>- **3 分 (合格)**: 排查路径存在部分迂回，但在步数限制内完成闭环。<br>- **2 分 (混乱)**: 在不相关的多个文件间盲目乱翻，多次使用 `write_file` 尝试盲改。<br>- **1 分 (失控)**: 出现死循环硬撞、无视工具报错或偏离用户初始目标。 |
| **事实收敛与总结 (Wrap-up Delivery)**| - **5 分 (卓越)**: 详尽说明 Bug 真实根因、修改点前后比对、测试覆盖情况及后续防范建议。<br>- **4 分 (良好)**: 清晰解释了改动点与验证结果。<br>- **3 分 (合格)**: 简要说明已完成修改，提供了基本 diff 说明。<br>- **2 分 (粗糙)**: 仅有一句敷衍的“已修复”，缺少代码事实细节支撑。<br>- **1 分 (空缺)**: 毫无总结返回，或返回截断乱码。 |

---

### 4.3 人机协同交互体验打分 (Human-in-the-Loop Protocol, 权重 15%)
度量智能体在真实终端人机协作过程中的友好度：

| 评估指标 | 得分标准 | 扣分项规则 |
| :--- | :---: | :--- |
| **开发者审批疲劳度 (Fatigue)** | 满分 5 分 | 在 AUTO 模式下非高危命令自动放行；在 ASK 模式下仅对关键修改弹窗。<br>若对 `git status` 等只读命令频繁弹窗打扰，每次扣 1 分。 |
| **物理回滚精准度 (Undo Accuracy)** | 满分 5 分 | 用户输入 `/undo` 时，磁盘文件毫秒级恢复初始状态得满分 5 分；若残留临时文件或未还原扣 5 分。 |
| **终端展示直观度 (CLI Rendering)**| 满分 5 分 | Rich 彩色卡片排版规范、Diff 高亮对比鲜明、仪表盘实时更新得 5 分；排版错乱扣 2 分。 |

---

### 4.4 综合评分卡 (Agent Capability Scorecard) 与权重计算

每个评测任务的综合得分（$S_{\text{task}}$）按以下公式标准化计算（百分制）：

$$S_{\text{task}} = \left( S_{\text{det}} \times 0.60 \right) + \left( \frac{S_{\text{judge}}}{15} \times 100 \times 0.25 \right) + \left( \frac{S_{\text{hitl}}}{15} \times 100 \times 0.15 \right)$$

- **$S_{\text{task}} \ge 90$**: **S 级 (生产级自主交付)** —— 具备工业级资深工程师水平，可全自动托管；
- **$80 \le S_{\text{task}} < 90$**: **A 级 (高效研发伙伴)** —— 极高成功率，微量人机干预即可合并代码；
- **$70 \le S_{\text{task}} < 80$**: **B 级 (初级助理水平)** —— 能够解决中低难度任务，复杂任务需人工审阅；
- **$S_{\text{task}} < 70$**: **C 级 (不合格)** —— 存在稳定性或决策质量短板，禁止生产直接投产。

### 5.1 评测环境标准化准备与隔离策略
为了保证评测结果的严格可复现性与环境无污染，评测作业必须遵循标准化沙箱流程：

```
  +--------------------------------------------------------------------------+
  |              Super-Harnes 自动化评测流水线 (Evaluation Pipeline)          |
  +--------------------------------------------------------------------------+
  | 1. 环境准备 (Setup)   ── 启动纯净沙箱，注入待测代码工程并复位 Git 提交   |

  +--------------------------------------------------------------------------+
```

3. **预算硬上限保护**: 默认设置基线总预算 `AGENT_TOTAL_BUDGET=200000`，步数上限设为对应题目要求（默认 10~15 步）；
4. **命令审批模式**: 评测自动化测试流水线强制配置 `APPROVAL_MODE=auto`。

## 6. 典型失效模式分类与归因排查手册 (Failure Taxonomy & Remediation Playbook)

在日常评测与大规模任务回归中，自主编码智能体常见的失败模式可归类为以下五类。本手册提供了详尽的现象特征、深层根因与调优应对措施：

---

### 6.1 模式一：工具振荡死循环 (Oscillation Loop)

#### 现象特征：
- 智能体在两个或三个工具间反复横跳（如 `grep_text` 查不到换 `find_by_name`，找不到又回 `grep_text`）；
- 或者同参反复调用 `read_file`；
- 步数迅速耗尽但没有任何实际代码修改产生。

#### 根因剖析：
1. **关键词提取假设偏差**: 用户描述中的模块名称与实际工程中的类名有微小拼写差异（如大小写、下划线）；
2. **工具 Schema 缺乏负向约束**: 模型未意识到目标文件已经被排除，盲目重复尝试；
3. **缺乏状态机约束**: 没有明确从 EXPLORE 到 MODIFY 的推进门槛。

#### Super-Harnes 调优与应对 SOP：
- **两级防线介入**:
  - 第 3 次循环时，`LoopDetector` 自动触发黄牌（WARNING），向模型注入反思提示：`【检测到重复排查停滞】...请停止盲目重试，建议使用 view_file_outline 或调整关键词`；
  - 第 4 次若继续振荡，出示红牌（FORCE_WRAPUP），强行关闭工具接口，迫使模型基于掌握的事实收尾并汇报困难。
- **系统调优**: 开启 `StageManager` 工具优先级重排，降低重复工具的注意力加权。

---

### 6.2 模式二：幻觉补丁与语法断裂 (Patch Hallucination & Syntax Break)

#### 现象特征：
- 智能体生成的 `apply_patch` 包含目标文件中根本不存在的代码行（SEARCH 块定位失败）；
- 补丁应用后导致 Python 代码括号未闭合、缩进混乱，直接触发 `SyntaxError`；
- 甚至导致原本正常通过的已有测试全部报红。

#### 根因剖析：
1. **未先读后改**: 模型凭借对常见开源库的预训练记忆“臆想”代码，未调用 `read_file` 查阅当前项目的真实代码切片；
2. **行号前缀污染**: 模型从 IDE 带行号的提示中复制了代码（如 `42 | def foo():`）；
3. **跨平台换行混淆**: Linux LF 与 Windows CRLF 换行符差异导致精准字符串匹配失败。

#### Super-Harnes 调优与应对 SOP：
- **内核确定性防御**:
  - `apply_patch` 自动执行正则行号剥离与全局 CRLF/LF 预归一化；
  - 补丁写入物理磁盘前，立即执行 `ast.parse` 语法自检；
  - 若自检报错，自动事务级全量回滚，绝不破坏磁盘，并将精准语法错误行号返回给 Agent。
- **System Prompt 约束**: 显式注入决策原则：`严禁未读先改；打补丁前必须至少一次精准查阅过目标行号区间`。

---

### 6.3 模式三：上下文注意力漂移与目标遗忘 (Context Attention Drift)

#### 现象特征：
- 会话交互经历多轮或长程排查（>15 轮）后，智能体开始偏离用户初始目标；
- 在不相关的辅助模块上消耗大量步数，甚至忘记了最初要修复哪个具体测试用例。

#### 根因剖析：
1. **长历史噪音挤占注意力**: 早期排查的几十个无用文件内容堆积在上下文中，稀释了用户核心意图；
2. **滑窗机械截断丢关键信息**: 简单从头部剔除消息导致用户最开始提出的详细需求被移出上下文；
3. **Prompt Cache 缓存位置不合理**: 动态信息插入在静态提示词前方，破坏了大模型服务端缓存。

#### Super-Harnes 调优与应对 SOP：
- **专款专用账本与工作记忆保全**:
  - `WorkingMemory` 中始终锁定保留 `current_goal`、`inspected_files` 与 `last_test_status`；
  - 逆向滑动窗口（SlidingWindow）始终成对保留最新交互，红区自动触发带轮次锚点的结构化增量纪要（如 `【历史排查纪要 (#1 ~ #8)】`）；
  - 轮内早期陈旧观察结果自动折叠裁剪（In-turn Pruning），释放宝贵上下文。

---

### 6.4 模式四：过早放弃与假性完成 (Premature Wrap-up & False Positives)

#### 现象特征：
- 智能体仅仅改完代码，未经任何测试或验证，便直接输出：“已成功为您修复此 Bug！”；
- 用户实际运行测试依然失败。

#### 根因剖析：
1. **缺乏闭环验证机制**: 模型在生成代码修改后缺乏自我怀疑态度，将“修改完毕”等同于“问题解决”；
2. **验证工具 Schema 优先级过低**: 模型注意力未聚焦在测试运行工具上。

#### Super-Harnes 调优与应对 SOP：
- **状态机阶段置顶重排**:
  - 任何代码修改成功（`apply_patch` / `write_file`）后，`StageManager` 立即将状态自动跃迁为 `TaskStage.VERIFY`；
  - 动态重排工具列表，将 `run_shell` 置顶，并注入引导 Banner：`【当前任务阶段: 验证闭环态 (VERIFY)】代码已修改完成，请优先运行 pytest 或构建命令进行闭环验证！`；
  - 形成强烈的引导驱动力，迫使模型调用验证命令确认结果全绿后再交付。

---

### 6.5 模式五：外部 MCP 进程僵死或通信异常 (MCP Subprocess Hangs)

#### 现象特征：
- CLI 启动时停滞数秒，甚至直接卡死在初始化阶段；
- 外部 MCP 服务由于写入过多 Stderr 日志导致管道缓冲区满而死锁。

#### 根因剖析：
1. **串行阻塞启动**: 多个外部子进程顺序启动，单个外部命令响应慢拖垮整体；
2. **操作系统管道缓冲区阻塞**: Stderr 管道未被持续异步排空，达到 64KB 缓冲上限后子进程挂起。

#### Super-Harnes 调优与应对 SOP：
- **并发握手与异步守护**:
  - `McpManager` 采用多线程并行并发发起子进程初始化；
  - 每一个外部进程配备独立守护线程持续排空 Stderr；
  - 握手超时或失败立即杀死并安全回收孤儿进程，确保主程序稳健运行。
